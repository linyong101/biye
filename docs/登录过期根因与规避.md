# 登录过期（401 "未登录或登录已过期"）根因与规避

> 文档定位：说明 Vigil 平台「前端反复提示登录过期 / 401」的真正成因，以及已落地的根治方案与日常规避动作。
> 适用角色：开发、答辩演示、运维。

---

## 一、现象

前端（5173）打开后偶发弹出「登录过期 / 未登录」，被强制跳回登录页；用 `admin / admin123` 重新登录后又正常。

---

## 二、认证机制（必读，才能理解根因）

| 环节 | 行为 | 代码位置 |
| --- | --- | --- |
| token 存储 | 浏览器 `localStorage` 键 `vigil:token`，刷新不丢 | `apps/dashboard/src/lib/api.ts` |
| token 有效期 | JWT **7 天**，密钥固定（`vigil-dev-secret-change-me`，见 `.env`） | `apps/server/src/services/auth.ts` |
| 全局守卫 | 仅校验 JWT 签名 + 是否过期，**不查数据库** | `apps/server/src/app.ts:32-39` |
| 真正的 401 来源 | `/api/auth/me` 按 token 里的 `sub`（= 用户 id）查库，**查不到用户即 401** | `apps/server/src/routes/auth.ts:80-82` |
| 前端反应 | 收到任意 401 → `clearToken()` + 跳 `/login` | `apps/dashboard/src/lib/api.ts` |

> 结论：单纯的「重启后端」**不会**让 token 失效（密钥固定）。所谓「重启后能用了」，真实原因是**重置流程里重新登录了一次**，拿到了与新 admin id 匹配的新 token。

---

## 三、根因（为什么"反复"）

核心矛盾：**登录态能否续命，取决于浏览器 token 的 `sub` 是否与数据库里的 admin `id` 一致**。

而历史上「处理登录问题」的标准动作是**删库重置**（`del dev.db` → `db:push` → `seed` → `dev`）。`ensureDefaultAdmin()` 每次重建 admin 时，会生成一个**新的随机 id（cuid）**。于是：

```
删库重置
  → 后端启动，ensureDefaultAdmin() 新建 admin，生成【新的随机 id】
  → 浏览器 localStorage 里还留着【上一次登录的旧 token】
       （7 天有效、签名有效，能过全局守卫）
  → 请求 /api/auth/me → 用旧 token 的【旧 id】查库 → 用户不存在 → 401
  → 前端收到 401 → clearToken() + 跳 /login → 显示「登录过期」
  → 重新用 admin/admin123 登录 → 拿到【新 id】token → 正常
  → 下次再删库重置 → 整段重演 → 看似「一直反复」
```

**额外的真实隐患**：测试引导 `test/setup.ts` 原先用 `process.env.DATABASE_URL ?? '...'` 设置测试库，但由于 **ESM 的 `import` 会被提升到赋值语句之前执行**，`PrismaClient` 在环境变量被设置前就已实例化，实际连的是 **开发库 `dev.db`**。一旦运行 `npm run test:server`，`setup.ts` 的 `deleteMany` 会**清空开发库的 user 表（含 admin）**，再次触发登录过期。

---

## 四、已落地的根治方案

1. **固定默认 admin 的 id**（`apps/server/src/services/auth.ts`）
   - 新增常量 `DEFAULT_ADMIN_ID = 'admin-default'`。
   - `ensureDefaultAdmin()` 改为：按 `username='admin'` 查询；不存在则**以固定 id 创建**；存在但 id 为历史随机值则**统一更新为固定 id**（保留用户名/密码/角色）。
   - 效果：无论删库重建多少次，admin 的 id 永远相同，浏览器旧 token 的 `sub` 永远匹配 → **彻底不再因重置而过期**。

2. **测试强制使用独立库**（`apps/server/test/env.ts` + `package.json`）
   - 新增 `test/env.ts`，仅做一件事：在 **PrismaClient 实例化之前** 通过 `node --import` 最先注入 `DATABASE_URL='file:./test.db'`。
   - `test` 脚本改为 `node --import tsx --import ./test/env.ts --import ./test/setup.ts ...`。
   - 效果：测试连接独立的 `prisma/test.db`，**绝不会再误清开发库 `dev.db` 的 admin**。

---

## 五、日常规避（给使用者）

- **遇到「登录过期」**：先确认后端 3001 在跑（`netstat -ano | findstr ":3001"`）；在跑的话**直接刷新页面、用 `admin / admin123` 重新登录**即可，**不要**一上来就删库。
- **仅在「忘记密码 / 数据损坏」时才删库重置**，且删库后**必须重新登录一次**。
- **不要**把 `npm run test:server` 当成日常操作来"验证"，它只用于回归测试；日常联调用 `admin/admin123` 登录。
- 重置后若仍提示过期：检查是否浏览器开了隐私模式/清了站点数据（localStorage 被清）。

---

## 六、验证记录（示例）

- 修改后运行 `npm run test:server`，应全部通过，且**开发库 `dev.db` 的 admin 不受影响**。
- 后端重启日志应出现：`已将默认管理员账号 id 固定为 admin-default（根治重置后登录过期）` 或直接 `已创建默认管理员账号：admin / admin123`。
- 此后浏览器只要 7 天内、不手动清缓存，登录态可一直保持，删库重建也不断。
